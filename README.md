# KDB 单人口播短视频制作

把一条手机录制的单人口播，做成可以直接发布的竖屏短视频。

它覆盖的不只是“剪掉口癖、配上字幕”，而是从理解内容开始，完成克制剪辑、字幕、封面、必要的解释性图形、HDR 和声音处理、隐私清理、最终验收，以及经过单独确认后的平台发布。

这个 Skill 来自连续多期真实视频的制作和返工。它不承诺一键生成，也不要求每条视频套用同一种模板。重点是让 Agent 先看懂你在讲什么，再决定哪些地方该剪、该解释、该保留。

## 它适合什么任务

当你已经录好一条视频，并希望得到一条完整成片时，可以使用这个 Skill。

典型输入是一条普通话为主的手机自拍视频。你可以明确告诉 Agent：

- 这一遍讲得已经很好，只删明显停顿；
- 可以大胆重组，但不要改变原意；
- 加字幕，图解只在真正帮助理解时出现；
- 不使用云端 ASR（自动语音识别）或 API key；
- 做好后上传到 YouTube Shorts，并添加指定的 Related Video（相关视频）。

它不负责多人访谈、高光集锦、文章、长视频标题等广义内容资产。那些任务更适合 [`lizheng-video-editing`](https://github.com/sunyuzheng/lizheng-video-production)。如果口播底片已经完全锁定，只剩 [HyperFrames](https://github.com/heygen-com/hyperframes) 图形包装，并且你的环境已经安装 `talking-head-recut`，可以直接使用后者。

## 一条视频会经历什么

Skill 不把流程写成固定 SOP，但有几条依赖关系不能颠倒：

1. **先看完，再判断。** Agent 会先检查素材、离线转写并理解完整内容，之后才决定开头、结构、剪辑和图形。
2. **先锁定口播，再绑定时间。** 字幕和复杂动画依赖稳定的成片时间线；内容还在移动时，不应过早锁死全局时码。
3. **先验收成片，再考虑发布。** 渲染成功不等于交付成功。最终 MP4 还要检查颜色、声音、字幕、遮脸、首尾黑帧、隐私和音画同步。
4. **发布是单独动作。** Agent 会先展示完整发布信息；只有得到明确确认，才会上传或公开。

具体实现可以随素材和本地工具变化。讲得连贯的视频可能只需要极轻剪和字幕；抽象结构比较多的视频，才值得加入章节导航、关系图或重新绘制的界面。

## 核心判断

### 开头不是随便抽一段“高光”

好的开头会让观众形成一个准确、值得继续的预期。观众应该知道自己正在看什么，同时留下一个正文确实会回答的问题。

如果观众只是“不知道这条视频到底在讲什么”，那不是好奇，而是困惑。

### 剪辑强度由素材决定

本来就讲得顺的内容，不需要为了显得专业而密集跳剪。明显的预卷、尾巴、假启动、独立口癖、无关支线或已经被正确版本替代的口误可以去掉；有效停顿、强调、个性和自然口语应该留下。

这里没有固定删除比例，也没有必须压到多少秒的目标。

### 图形必须完成一项工作

每一个视觉节点都应该能够回答：如果没有它，观众会误解或错过什么？

合理的用途包括：

- 交代主题或章节；
- 解释关系、流程、层级或抽象概念；
- 展示真实照片、结果或界面；
- 遮盖真实跳剪、甩镜或敏感屏幕；
- 强调一条值得记住的结论。

如果答案只是“看起来更像做过后期”，那就不加。

### 技术交付也是成片的一部分

iPhone 的 HLG / Dolby Vision 不能只靠修改颜色标签变成 SDR；否则人物很容易发白或过亮。相机文件还可能带有 GPS、设备、拍摄时间和额外数据轨。字幕、响度、首帧封面和音画时长也都需要在最终编码文件上检查。

因此，Skill 不会直接把原始手机 MOV 上传到公开平台。

## 最终产物

一次完整运行通常会留下：

- 可直接上传的 9:16 MP4；
- 与视频第一个编码帧一致的封面 JPEG；
- 已校正、按剪后时间线重映射的 SRT；
- 原始和精校转写；
- 内容地图、剪辑决定和时间映射；
- 当前可编辑工程或干净 A-roll；如果使用了图形，则包含 HyperFrames 工程；
- 技术、视觉、语义和隐私验收记录；
- 可选的“下次怎么讲更好”简短建议；
- 发布后的视频链接和平台核验记录（如果执行了发布）。

## 安装

将仓库克隆到 Codex 的 skills 目录：

```bash
git clone https://github.com/sunyuzheng/kdb-talking-head-short-production.git \
  ~/.codex/skills/kdb-talking-head-short-production
```

如果你维护统一的 Skills 目录，也可以先把仓库克隆到那里，再从 `~/.codex/skills/` 建立符号链接。

### 运行条件

这个仓库提供的是 Agent 的判断、执行边界和验收规则，不捆绑视频处理软件。运行时需要检查当前环境里可用的媒体探测与编码工具、本地中文 ASR 和对齐器，以及可选的 HyperFrames 渲染器。

缺少依赖时，Agent 应该说明缺什么，而不是默默把素材发到云端。YouTube 发布还需要一个已经登录、可由当前环境控制的 YouTube Studio 浏览器会话。

## 使用

在 Codex 中直接点名：

```text
使用 $kdb-talking-head-short-production 处理这条视频。

我觉得自己从头到尾讲得挺好，不要过分精编。只删明显停顿、假启动，
以及我明确标记为不保留的内容。
加适合手机屏幕的字幕；插图只有真正帮助理解叙事时才使用。
本地中文 ASR，不要 API key。先给我预览，不要发布。
```

如果需要上传，可以在成片验收后继续说：

```text
把最终版上传到 YouTube Shorts。标题、简介、可见性、字幕和 Related Video
先完整列给我确认，确认后再执行。
```

## 真实返工留下的经验

这份 Skill 记录的失败模式都实际发生过：

- 把一段看似有冲击力的话抽到开头，却因为缺少上下文反而劝退观众；
- 手机上看起来精致的字，实际小到无法阅读；开场大卡片还可能直接遮住人物的眼睛和嘴；
- `02 / 03`、`03 / 03` 这样的章节编号被浏览器错误断行；
- 字幕的起点和终点映射到了不同保留段，导致一句字幕停留几十秒；
- HLG 只改标签后，人物肤色发白、画面过亮；
- 编辑器里看起来正常，最终编码文件却出现首尾、遮挡或时长问题。

这些经验被写成判断和验收标准，而不是固定模板。更多案例在 [`editorial.md`](references/editorial.md) 和 [`delivery.md`](references/delivery.md)。下一条视频如果有更好的理由，可以采用不同做法。

## 隐私与发布边界

本仓库不包含任何原始 MOV、成片、私人转写、GPS、API 凭证、浏览器状态或平台 Cookie。

处理时，原始素材保持只读，派生文件写入项目目录。公开交付前需要清除定位、设备、拍摄时间和额外数据轨，并处理画面中的敏感信息；原始手机文件不会直接上传。

Skill 默认使用本地中文 ASR 和本地媒体处理。平台发布必须单独展示目标频道、文件、标题、简介、可见性、受众、字幕、Related Video 和其他重要设置，并获得针对这份发布信息的明确批准。
